# java-chat-server

一个基于 Java 原生 Socket + MyBatis 的多用户 TCP 聊天服务端，用于展示并发连接管理、有界队列背压、慢客户端隔离等后端基础问题的分析与修复过程。

## 功能特性

- 用户注册 / 登录 / 登出（AccountService 承载注册与凭据校验，密码 MD5 摘要存储，MyBatis + MySQL）
- 在线用户查询
- 点对点私信与在线群发转发（消息正文支持逗号，群发不回显给发送者）
- 并发登录防护：同一账号同时只允许一个连接在线
- 每连接独立写线程 + 有界出站队列，隔离慢客户端，避免阻塞全局转发
- 共享消息队列有界（1024），满载时快速拒绝
- 读空闲超时（默认 60 秒）自动清理失联连接

## 环境要求

- JDK 22+、Maven 3.9+
- Docker 与 Docker Compose（用于 MySQL 8.4）

## 快速开始

### 1. 数据库配置

在项目根目录创建 `.env`（供 Compose 初始化 MySQL 使用）：

```dotenv
MYSQL_ROOT_PASSWORD=<root密码>
MYSQL_PASSWORD=<chat_user密码>
```

复制数据库连接配置示例并填写密码：

```
cp src/main/resources/mysql.properties.example src/main/resources/mysql.properties
```

编辑 `mysql.properties`，将 `jdbc.password` 改为与 `.env` 中 `MYSQL_PASSWORD` 一致的值。

> 注意：Compose 环境变量和初始化脚本只在空数据卷首次初始化时生效；`mysql.properties` 是 Java 应用的连接配置，修改它不会更改已存在的 MySQL 账户密码。

### 2. 启动 MySQL

```bash
docker compose up -d
docker compose ps
```

- 镜像 `mysql:8.4`，宿主机 `127.0.0.1:3307` 映射到容器 3306。
- 数据库 `chat-app`、应用账户 `chat_user` 由首次初始化自动创建。
- 初始化 SQL 位于 `docs/sql/chat-app.sql`（创建 `user` 表），数据持久化在命名卷 `mysql_data` 中。

### 3. 启动服务端

```bash
mvn compile
```

运行入口类 `com.kiyasu.chat.controller.Server`。服务端监听 TCP 端口 `23456`，客户端必须使用同一端口。

### 4. 连接测试

项目不内置客户端，可用任意 TCP 文本工具（如 `nc`、telnet 或自写客户端）连接 `127.0.0.1:23456`：

1. 连接后服务端发送欢迎语，客户端需先发送一个**空行**跳过提示；
2. 之后每条命令占一行，以换行结束。

一个最小会话示例：

```
S: 这里是kiyasu的聊天室, 输入回车继续...
C:（空行）
S: 请输入命令:
C: 002,Alice,password
S: 102,SUCCESS,登录成功
C: 004
S: 104,SUCCESS,Alice,Bob
C: 005,Alice,Bob,hello,world
S: 000,SUCCESS,消息已加入发送队列
（Bob 连接收到）106,Alice,Bob,hello,world
C: 006,hello,everyone
S: 000,SUCCESS,消息已加入发送队列
（Bob 连接收到）105,Alice,hello,everyone
C: 003,Alice
S: 103,SUCCESS,登出成功
```

## 协议说明

所有命令与响应均为单行 UTF-8 文本，以换行结束，字段以英文逗号分隔。服务端输出统一以 LF（`\n`）结束，不依赖服务器操作系统；客户端请求可使用 LF 或 CRLF，服务端按行读取兼容两者。

### 客户端 → 服务端

| 命令码 | 含义 | 格式 | 说明 |
|---|---|---|---|
| 001 | 注册 | `001,<id>,<password>` | id 已存在则失败 |
| 002 | 登录 | `002,<id>,<password>` | 同一账号重复登录返回"用户已在线" |
| 003 | 登出 | `003,<id>` | 只能登出当前连接自己的账号 |
| 004 | 查询在线用户 | `004` | 命令码后内容被忽略 |
| 005 | 发送私信 | `005,<src>,<dst>,<message>` | `<message>` 中的逗号全部保留；src 必须与登录身份一致 |
| 006 | 发送群发消息 | `006,<message>` | 发送者取自当前登录会话；`<message>` 中的逗号全部保留 |

命令码解析时仅对命令码本身去除首尾空白；未知命令码不会断开连接，返回错误响应。

### 服务端 → 客户端

| 响应码 | 含义 | 格式 |
|---|---|---|
| 101 | 注册结果 | `101,SUCCESS\|FAIL,<说明>` |
| 102 | 登录结果 | `102,SUCCESS\|FAIL,<说明>` |
| 103 | 登出结果 | `103,SUCCESS\|FAIL,<说明>` |
| 104 | 在线用户列表 | `104,SUCCESS,<id1,id2,...>`；无在线用户时为 `104,SUCCESS,当前没有在线用户` |
| 105 | 转发的群发消息 | `105,<src>,<message>`（推送给除发送者外的其他在线用户） |
| 106 | 转发的私信 | `106,<src>,<dst>,<message>` |
| 000 | 通用提交确认 / 错误 | 如 `000,SUCCESS,消息已加入发送队列`、`000,FAIL,命令解析错误`、`000,FAIL,接收者离线` |

命令整体无法解析时（空行、缺少命令码等），返回 `000, 命令格式错误`（注意响应说明文本中的标点为半角逗号加空格）。

## 线程与容量模型（概览）

| 组件 | 数量 / 容量 | 说明 |
|---|---|---|
| 连接处理线程池 | 固定 30 线程 | 每个连接占用一个线程直至断开；满载时超额连接立即关闭 |
| 消息转发线程 | 1 | 从共享消息队列取消息并投递到目标连接 |
| 共享消息队列 | 1024 | 满载时新消息被拒绝，返回"服务器繁忙" |
| 每连接出站队列 | 256 | 满载时该条消息被丢弃；丢弃日志按接收者聚合为 WARN |
| 读空闲超时 | 60 秒 | 超时未收到任何数据即清理连接 |

详细设计、并发语义与取舍见 [docs/design.md](docs/design.md)。

## 实测与验证边界

以下数据来自 2026-10-31 与 2026-11-03 的本机实测，服务端和负载生成器均走**单机 loopback**，只用于说明行为与量级，不代表公网、多机部署或大量活跃连接的容量承诺。

| 场景 | 实测结果 |
|---|---|
| 40 个并发 TCP 连接 | 30 个立即获得服务（等于线程池大小），10 个在线程池队列等待；释放 10 个活跃连接后，等待连接 10/10 获得服务 |
| 24 账号并发注册与登录 | 注册、登录均 24/24 成功；重复登录、错误密码、在线列表与登出行为符合预期 |
| 10 对客户端持续收发 15 秒 | 58,755 条消息，约 3,916 msg/s；p50 0.3 ms、p95 0.6 ms；ACK 与接收端送达数一致，未触发入站队列满载 |
| 6 个发送端向慢接收端发送 10 秒（日志聚合后复测） | 24,294 次入队成功，接收端恢复读取后收到 5,423 条，18,871 条因出站队列饱和被丢弃；聚合计数为 18 次千条汇总 + 871 条尾数，丢弃类日志共 20 条 WARN |

AccountService 拆分后的端到端验证已覆盖注册、重复注册、错误密码、正确登录、重复登录和登出；重复注册第二次返回 `101,FAIL,用户ID已存在`。手工验证还覆盖在线查询、消息转发、离线列表更新、约 60 秒读超时清理与断连后的写线程回收。

尚未覆盖公网或跨机网络、长时间老化、1024 入站队列满载的端到端复现，以及完整服务优雅关闭。

## 已知限制

- **入队成功不等于送达**："消息已加入发送队列"仅表示消息进入服务端内部队列；目标连接出站队列满时消息会被丢弃。
- 面向小规模演示场景：固定 30 个连接处理线程、单转发线程，未针对大量活跃连接设计；上述吞吐与延迟仅是同机 loopback 观测值。
- 服务端没有完整的优雅关闭流程；发送线程收到中断即退出，不保证关闭前排空队列。
- 消息不做离线持久化：单聊接收者离线即返回失败；群发仅投递给转发时刻在线的其他用户。
- Java 端数据库配置仍读取 `src/main/resources/mysql.properties`，未改为读取环境变量。
- 密码使用 MD5 摘要存储；生产场景应使用 BCrypt 等自适应哈希。
